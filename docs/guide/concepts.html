How the pieces fit구성 요소가 맞물리는 방식

Two layers, one naming rule, one manifest.두 계층, 이름 규칙 하나, 매니페스트 하나.

The two layers두 계층

python-multiplatform — the binder — embeds CPython in a Kotlin Multiplatform app and exposes Kotlin declarations to Python under their Kotlin names: androidx.compose.material3 is androidx.compose.material3. It never renames a namespace.

python-multiplatform — 바인더 — 는 Kotlin Multiplatform 앱에 CPython 을 임베딩하고, Kotlin 선언을 Kotlin 이름 그대로 파이썬에 노출합니다: androidx.compose.material3 는 androidx.compose.material3 입니다. 네임스페이스 이름을 절대 바꾸지 않습니다.

pythonx-compose — this package — is real Python on disk. Its modules import those androidx.compose.* modules and restructure them into pythonx.compose.*.

pythonx-compose — 이 패키지 — 는 디스크에 있는 실제 파이썬입니다. 이 패키지의 모듈이 androidx.compose.* 를 import 해 pythonx.compose.* 로 재구성합니다.

The naming rule이름 규칙

Expose the original Kotlin declarations and parameters with Pythonic names. A name that starts upper-case — a type, an object, a composable — keeps its Kotlin spelling. Every other name is reached by its snake_case spelling only; the camelCase spelling is not a second name. An explicit overload keeps its type suffix.

Kotlin 의 원래 선언과 매개변수를 파이썬다운 이름으로 노출합니다. 대문자로 시작하는 이름 — 타입, 객체, 컴포저블 — 은 Kotlin 표기를 유지합니다. 그 밖의 이름은 snake_case 표기로만 접근하며, camelCase 표기가 또 하나의 이름이 되지는 않습니다. 명시적 오버로드는 타입 접미사를 유지합니다.

KotlinPython
onClickon_click
fillMaxWidthfill_max_width
horizontalAlignmenthorizontal_alignment
zIndexz_index
toURLStringto_url_string
padding__Dppadding__Dp
ModifierModifier
ArrangementArrangement

The rule is applied forward to the module's real Kotlin names and never inverted, so a name the reverse rule could not reconstruct (to_url_string) still resolves. Keyword arguments to a module function are snake_case too (padding_values= reaches paddingValues), and inspect.signature reports the snake_case names, with python_multiplatform.KOTLIN_DEFAULT as the default of every parameter Kotlin defaults.

규칙은 모듈의 실제 Kotlin 이름에 정방향으로만 적용되고 역으로 계산하지 않으므로, 역규칙으로는 복원할 수 없는 이름(to_url_string)도 해석됩니다. 모듈 함수의 키워드 인자도 snake_case 이며(padding_values= 가 paddingValues 에 닿음), inspect.signature 는 snake_case 이름을 보여 주고 Kotlin 이 기본값을 가진 매개변수에는 python_multiplatform.KOTLIN_DEFAULT 를 기본값으로 보여 줍니다.

The user's notebook writes signatures such as Button(onclick, corner_radius, color). Those are naming examples; where they differ from Kotlin, the Kotlin parameter, snake-cased, wins.

사용자 노트북은 Button(onclick, corner_radius, color) 같은 시그니처를 씁니다. 이는 이름 예시이며, Kotlin 과 다르면 Kotlin 매개변수를 snake_case 로 바꾼 것이 이깁니다.

One re-export rule재노출 규칙 하나

Every module in pythonx-map.toml is a real file on disk whose __init__.py is one line. Nothing is resolved at import; a name is looked up in the mapped Kotlin package the first time it is read, and then lives in the module like any attribute. There is no per-widget wrapper.

pythonx-map.toml 의 모든 모듈은 디스크에 있는 실제 파일이며, __init__.py 는 한 줄입니다. import 할 때는 아무것도 해석하지 않고, 이름을 처음 읽을 때 대응된 Kotlin 패키지에서 찾은 뒤 보통의 속성처럼 모듈에 남습니다. 위젯별 래퍼는 없습니다.

# pythonx/compose/material3/__init__.py
from pythonx.compose._reexport import reexport

__getattr__, __dir__ = reexport(__name__)

Extension functions are methods확장 함수는 메서드

Most of Modifier is Kotlin extension functions. In Python each one is a method on the receiver's proxy, so a chain reads as it does in Kotlin. The binder's proxy class keeps Kotlin names; the same naming rule is registered as the binder's member resolver, so the snake_case spelling reaches the Kotlin member.

Modifier 의 대부분은 Kotlin 확장 함수입니다. 파이썬에서는 각각이 수신 객체 프록시의 메서드가 되어, 체인이 Kotlin 에서처럼 읽힙니다. 바인더의 프록시 클래스는 Kotlin 이름을 유지하며, 같은 이름 규칙이 바인더의 멤버 리졸버로 등록되어 snake_case 표기가 Kotlin 멤버에 닿습니다.

Modifier.padding(16).size(24).fill_max_width()

Keyword arguments to such a method are snake_case too — m.padding(padding_values=…), as the module function takes padding(m, padding_values=…). The resolver also hands the binder a keyword map read from the declaration's own parameter names. Kotlin's spelling (paddingValues=) still works at run time; the type stubs offer only the Pythonic one.

이런 메서드의 키워드 인자도 snake_case 입니다 — m.padding(padding_values=…) 이며, 모듈 함수는 padding(m, padding_values=…) 를 받습니다. 리졸버는 선언의 실제 파라미터 이름에서 읽은 키워드 맵도 바인더에 넘깁니다. Kotlin 이름(paddingValues=)도 실행 시에는 그대로 통하지만, 타입 스텁은 Pythonic 이름만 제시합니다.

Kotlin objectsKotlin 객체

Alignment and Arrangement are Kotlin objects, served as namespaces read by the same rule. Constants keep their Kotlin spelling and are read without parentheses; functions inside the object are snake_case.

Alignment 와 Arrangement 는 Kotlin 객체이며, 같은 규칙으로 읽는 네임스페이스로 제공됩니다. 상수는 Kotlin 표기를 유지하고 괄호 없이 읽으며, 객체 안의 함수는 snake_case 입니다.

from pythonx.compose.ui import Alignment
from pythonx.compose.layout import Arrangement

Alignment.Center
Arrangement.End
Arrangement.spaced_by(8)
Alignment.Horizontal.End      # the same constant as Alignment.End

A constant can also be read grouped by its declared type, as the notebook writes it: Alignment.Horizontal.End is Alignment.End, read the same way. A group holds only the constants declared as exactly that type, so Alignment.Center (declared Alignment) is in no group, and Arrangement.SpaceBetween is under Arrangement.HorizontalOrVertical, not Arrangement.Horizontal.

노트북처럼 상수를 선언된 타입별로 묶어서 읽을 수도 있습니다. Alignment.Horizontal.End 는 Alignment.End 이며 같은 방식으로 읽힙니다. 묶음에는 정확히 그 타입으로 선언된 상수만 들어가므로 Alignment.Center(선언 타입 Alignment)는 어느 묶음에도 없고, Arrangement.SpaceBetween 은 Arrangement.Horizontal 이 아니라 Arrangement.HorizontalOrVertical 아래에 있습니다.

Value classes값 클래스

Dp wraps a single float, so a raw number may stand for it: padding(16) means padding(16.dp). That permission is the manifest's allowlist, handed to the binder when a pythonx.compose module first resolves a name. Color and TextUnit pack several fields into one value, so a raw number would decode as something else entirely — they are refused, with a message saying why. A colour is written through Kotlin's own factory: Color(0xFFFF0000).

Dp 는 float 하나를 감싸므로 숫자로 쓸 수 있습니다: padding(16) 은 padding(16.dp) 입니다. 이 허용은 매니페스트의 허용 목록이며, pythonx.compose 모듈이 처음 이름을 해석할 때 바인더에 전달됩니다. Color 와 TextUnit 은 여러 필드를 한 값에 담으므로 숫자를 넣으면 전혀 다른 값으로 해석됩니다 — 그래서 이유를 밝히며 거절합니다. 색은 Kotlin 자신의 팩토리로 씁니다: Color(0xFFFF0000).

One manifest, two readers매니페스트 하나, 읽는 쪽 둘

pythonx/compose/pythonx-map.toml says which pythonx.compose.* module stands for which Kotlin package; it lives inside the package and ships in the wheel. The runtime and the .pyi generator read the same file, so the name your editor completes is the name the interpreter resolves. Stubs generated from real Compose, and py.typed, are not shipped yet (issue #12).

pythonx/compose/pythonx-map.toml 이 어떤 pythonx.compose.* 모듈이 어떤 Kotlin 패키지에 대응하는지 적습니다. 이 파일은 패키지 안에 있고 wheel 에 함께 담깁니다. 런타임과 .pyi 생성기가 같은 파일을 읽으므로, 편집기가 완성하는 이름과 인터프리터가 해석하는 이름이 같습니다. 실제 Compose 에서 생성한 스텁과 py.typed 는 아직 함께 배포되지 않습니다(이슈 #12).

@Composable@Composable

The decorator stays, and it is an identity: it returns the function unchanged. The composer each nested call needs is threaded by the binding from the callee's declared parameters, never by anything the caller does.

데코레이터는 유지되며 항등 함수입니다: 함수를 그대로 돌려줍니다. 중첩 호출마다 필요한 composer 는 호출되는 쪽의 선언된 매개변수를 보고 바인딩이 넘기며, 호출하는 쪽은 아무것도 하지 않습니다.
